## Context

当前系统提供两种匹配模式：
1. **单知识点匹配** (`/api/match`)：返回按综合分排序的扁平列表
2. **综合知识点匹配** (`/api/match/composite`)：返回涉及多个知识点的代码片段

两种模式都使用相同的打分公式：`score = 0.2×AST + 0.7×关键词 + 0.1×难度`

教育场景需要按难度分级展示代码示例，但当前 API 无法直接支持此需求。

## Goals / Non-Goals

**Goals:**
- 提供按难度分级的矩阵返回格式
- 支持单知识点和综合知识点两种场景
- 矩阵模式下只关注语义相关性（难度作为分类维度）
- 保持向后兼容，不破坏现有 API

**Non-Goals:**
- 不修改现有列表模式的行为
- 不支持超过 3 个难度级别的自定义分级（MVP 阶段）
- 不实现前端界面（仅后端 API）

## Decisions

### 决策 1：矩阵模式下移除难度权重

**选择**：矩阵模式使用归一化权重 `w_ast=0.22, w_keyword=0.78, w_difficulty=0.0`（基于生产配置 0.2/0.7 归一化）

**理由**：
- 难度已作为分类维度（矩阵行标签），再参与打分会造成职责重叠
- 用户选择某个难度级别时，更关心语义相关性而非难度值精确度
- 避免"双重惩罚"：例如 easy 桶内难度偏高的片段不应被降权

**备选方案**：
1. 保留难度权重 → 同一桶内仍按难度微调排序，但概念不清晰
2. 完全移除难度 → 采用此方案，职责分离更清晰

### 决策 2：默认难度分级边界

**选择**：三级分类
- `easy`: 难度值 [0, 0.33)
- `medium`: 难度值 [0.33, 0.66)
- `hard`: 难度值 [0.66, 1.0]

**理由**：
- 等分三级符合教育领域常见分类（初级/中级/高级）
- 边界清晰，易于理解和调试

### 决策 3：API 路径设计

**选择**：使用独立端点 `/api/match/matrix` 和 `/api/match/composite/matrix`

**理由**：
- 返回结构不同（矩阵 vs 列表），使用独立端点更清晰
- 避免通过查询参数切换返回格式导致的复杂性
- RESTful 风格，资源语义明确

**备选方案**：
1. 使用查询参数 `?format=matrix` → 同一端点返回不同结构，客户端处理复杂
2. 使用独立端点 → 采用此方案，更符合 REST 语义

## Risks / Trade-offs

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 某些难度级别结果为空 | 矩阵不完整 | 返回空数组，前端展示"暂无示例" |
| 难度分布不均匀 | 某级别片段过多/过少 | `per_level` 参数限制每级别数量 |
| 自定义分级需求 | MVP 不支持 | 预留 `levels` 参数，后续版本实现 |

## Migration Plan

无迁移需求，纯增量变更。
