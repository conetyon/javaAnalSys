# Proposal: AI 解释缓存与性能优化

## 背景

当前 AI 代码解释功能存在以下用户体验问题：

1. **响应慢**：每次请求都调用 LLM，平均响应时间 15-30 秒
2. **刷新丢失**：页面刷新后 AI 解释消失，需重新生成
3. **登录过期丢失**：Token 过期后重新登录，之前的解释全部丢失
4. **重复计算**：同一代码片段 + 知识点的解释被多次生成，浪费 LLM 资源

## 目标

1. **缓存命中时**：毫秒级返回（< 500ms）
2. **减少 LLM 调用**：相同请求复用缓存，节省成本
3. **跨会话持久化**：刷新/重新登录后仍可快速加载
4. **配额优化**：从缓存读取不消耗用户配额

## 解决方案

### 后端缓存机制

1. **缓存存储**：新建 `explain_cache` 表
2. **缓存 Key**：`(snippet_id, kp_ids_hash, user_level)` 组合
3. **缓存内容**：完整的 AI 解释文本
4. **缓存策略**：
   - 命中：直接返回缓存内容（SSE 格式）
   - 未命中：调用 LLM 并存储结果

### 前端优化

1. **缓存状态提示**：显示"来自缓存"或"实时生成"
2. **强制刷新按钮**：允许用户重新生成解释
3. **LocalStorage 备份**：本地缓存最近查看的解释

## 涉及模块

- `src/services/explain_service.py` - 添加缓存读写逻辑
- `src/db_manager/database.py` - 新增 `explain_cache` 表
- `api/routes/explain.py` - 缓存命中时跳过配额检查
- `frontend/src/components/CodeExplainer.tsx` - 缓存状态 UI

## 风险与考虑

1. **缓存一致性**：知识点更新后需清除相关缓存
2. **存储增长**：需要定期清理过期缓存
3. **user_level 差异**：不同难度级别需分别缓存

## 时间线

- 迭代 1：后端缓存基础功能（数据库存储）
- 迭代 2：前端缓存状态 UI + 强制刷新
- 迭代 3：性能监控 + 缓存清理策略
